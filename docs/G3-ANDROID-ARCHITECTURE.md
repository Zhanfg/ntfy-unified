# G3 Android architecture baseline (0.0.3)

G2 was externally accepted (PR #4) and promoted to main by release PR #6.

## Shared modules
- Protocol: existing Rust ntfy::http and ntfy::service (TLS, Basic/Bearer,
  replay cursor, dedup, reconnect/backoff). They are NOT duplicated in JS.
- SQLCipher persistence: existing db + storage::encryption, app-private data dir.
- Android credentials: keyring-core / android-native-keyring-store 1.0.0, which
  keeps the database key encrypted by a real Android Keystore entry.
  No plaintext fallback is allowed.
- Notifications: existing tauri-plugin-notification; default generic preview,
  preference-controlled payload, muted topic and schedule preserved.
- UI: existing React/Next.js in the Android WebView (no Svelte port).
- Desktop-only modules: system tray, autostart, window state, command-executing
  automations and hardware sound/screenshot actions are NOT built into Android.

## Current guarantees and limitations
This branch starts mobile adaptation. Android has NOT been built, signed or
device-tested until separate CI and supervisor evidence exists.

G3 is foreground only: no FCM, foreground service, guaranteed notifications
after Android process death, or long-running background guarantees.
Keyring security depends on the device's Keystore support. If unavailable,
startup fails rather than silently storing secrets in plaintext.

## Licensing

## Signing
No signing materials, passwords, debug keystores, private keys or placeholders
are committed or generated by the project. A CI native build is NOT a signed,
installable APK unless the later secure user-controlled signing procedure
actually succeeds. Do not publish unsigned output as a user-installable package.

## G3 Android notification channel and permission verification

The existing Settings form checks isPermissionGranted() and exposes a user-triggered
requestPermission() action. Android 13+ POST_NOTIFICATIONS is handled by the
Tauri 2 Notification plugin; CI examines the final merged APK manifest using
aapt2 dump permissions (not merely the plugin's source manifest).

The Android Rust adapter registers the dedicated ntfy-messages notification
channel on startup, with default importance and private lockscreen visibility.
Only notifications explicitly targeting that channel are posted. If channel
registration fails, startup stays available so normal ntfy reception works,
while the notification path reports a non-sensitive delivery failure.

On receiving a fresh message, SQLCipher persistence and the Inbox event happen
BEFORE checking Android system notification permission. When authorization is
Denied, Prompt or PromptWithRationale, or the channel is unavailable, the
system notification is suppressed; the message stays available in Inbox and
the existing ntfy:delivery-error event informs the user. No prompt is issued
automatically while processing incoming messages. Existing mute and schedule
policies, reconnect logic, and default generic privacy preview remain intact.

Host Rust unit tests cover the Granted, Denied, Prompt,
PromptWithRationale and unavailable-channel decisions; Android CI verifies
platform-separated command handlers, direct-route UI guards and merged
manifest permission. This is code/CI evidence, not device-notification E2E.
